Repository Architecture

1. Purpose

This document defines the organization of the SalvageCars.com source repository.

Its purpose is to ensure that the repository remains understandable, maintainable, and scalable as the platform grows.

The repository architecture should mirror the product architecture.

Developers and contributors should be able to understand where new content belongs without relying on tribal knowledge.

2. Repository Philosophy

The repository should evolve with the platform.

The structure should support future growth while remaining simple enough to maintain today.

Key principles include:

  • Organize by purpose rather than by file type.
  • Prefer readability over cleverness.
  • Keep related content together.
  • Avoid unnecessary complexity.
  • Introduce automation only when it simplifies maintenance.
  • Evolve gradually rather than rewriting existing work.

3. Repository Goals

The repository should:

  • Support rapid content creation.
  • Encourage consistency.
  • Keep documentation close to implementation.
  • Separate project documentation from public website content.
  • Make future automation straightforward.

6. Public Website

public/
├── index.html
├── questions/
├── states/
├── guides/
├── vision/
├── architecture/
├── privacy/

    ├── css/

The homepage contains the State Guidance directory; the individual jurisdiction pages and seven question journeys have their own directories.

7. Assets

The current public/assets/ directory has css/, images/, and js/ subdirectories. In the supplied website snapshot, these contain placeholder .gitkeep files rather than a developed shared asset library.

Reusable assets can be centralized here as the site evolves. Avoid creating extra asset directories without a practical need.

8. Guides

Educational guides live under public/guides/. The directory includes a guide index and a separate index.html for each guide.

public/guides/
├── index.html
├── how-to-buy-a-salvage-car/index.html
├── what-is-a-salvage-car/index.html
├── is-a-salvage-car-worth-it/index.html
└── state-and-auction-terms/index.html

This structure supports readable URLs and allows the guide library to grow by topic.

9. State Guidance

Jurisdiction guidance lives in public/states/, with a separate directory and index.html for each of the 50 states and the District of Columbia.

public/states/
├── new-hampshire/index.html
├── california/index.html
├── district-of-columbia/index.html
└── ... (48 additional jurisdictions)

The State Guidance directory is on the homepage at /#state-guidance; there is no separate state index page. Question journeys link to relevant sections within jurisdiction pages.

10. Question Journeys

The seven question journeys live under public/questions/. Each journey has its own directory and index.html.

public/questions/
├── can-my-vehicle-be-rebuilt/index.html
├── before-buying/index.html
├── back-on-the-road/index.html
├── out-of-state-vehicles/index.html
├── selling-or-transferring/index.html
├── title-brands/index.html
└── vehicle-inspections/index.html

Journey pages direct visitors to relevant sections of jurisdiction pages using state-specific anchors. The check-question-navigation.py script validates those links.

11. Future Repository Expansion

Additional directories may be introduced as corresponding features are developed. Potential examples include interactive tools, vehicle categories, structured data, templates, and further shared assets.

public/tools/           (potential)
public/categories/      (potential)
data/                   (potential)
templates/              (potential)

These examples are possibilities, not a description of implemented features or a commitment to particular directory names.

12. Legal and Public Policies

The Privacy Policy and Terms of Use are published as independent page directories rather than within a shared public/legal/ directory.

public/privacy/index.html
public/terms/index.html

Any additional policy or disclosure pages should be organized according to their actual published URLs.

13. Validation and Maintenance

Three scripts in the repository root support ongoing quality checks:

  • audit-state-pages.py — checks structural consistency across jurisdiction pages.
  • check-question-navigation.py — checks question-journey links to jurisdiction sections.
  • audit-site-links.py — checks internal links and anchors, including obsolete state-index references.

Validation scripts should remain easy to find and run as content and navigation change. The repository also contains audit reports and working notes, which can be reviewed during a separate cleanup pass.

14. Naming Standards

Directories should use lowercase, descriptive names with hyphens between words and should match public URLs where practical.

how-to-buy-a-salvage-car
can-my-vehicle-be-rebuilt
district-of-columbia

Use an index.html file within each published page directory to support clean URLs.

15. Evolution Strategy

The repository should evolve through incremental improvements.

Large-scale rewrites should be avoided unless they provide substantial long-term benefits.

When introducing new technologies, existing content should continue to function whenever practical.

16. Definition of Success

The repository architecture succeeds when:

  • Contributors know where new content belongs.
  • Similar content is organized consistently.
  • The structure mirrors the product.
  • Future automation can be added without major reorganization.
  • The repository remains understandable after years of growth.
