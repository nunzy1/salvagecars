SalvageCars.com Design System

Internal Design Document

Status: Draft   |   Version: 0.3

1. Purpose

This document defines the visual and interaction standards used throughout SalvageCars.com.

Its purpose is to create an experience that is clear, consistent, trustworthy, accessible, easy to scan, easy to navigate, and useful across devices.

The design system supports the product architecture and the user journeys defined elsewhere in the project documentation. It does not redefine the site's information architecture, navigation model, content strategy, or repository structure.

The design system should remain intentionally lightweight. New visual patterns and components should be introduced when they solve a recurring user, content, or interaction need.

2. Document Boundaries

To avoid duplication across internal project documentation, each document has a distinct responsibility.

  • Product Architecture defines the major product concepts, capabilities, and how the platform can evolve.
  • Site Structure & User Navigation defines information organization, Jobs To Be Done (JTBD), user journeys, navigation, internal linking, and how visitors move through the site.
  • Repository Architecture defines where source files and internal documentation belong in the repository.
  • Design System defines how information and interactions are presented visually and behaviorally.
  • Content Standards, when created, will define how SalvageCars.com content is written, including voice, terminology, editorial conventions, and writing guidance.

When another project document already owns a concept, this document should reference that concept rather than reproduce it.

Part I

Design Principles

3.1 Clarity Over Decoration

SalvageCars.com prioritizes understanding over visual decoration.

Design should help visitors understand information, recognize important information, find answers, compare information, make decisions, and determine what to do next.

Decoration should never compete with content. Pages should rely on typography, whitespace, hierarchy, and organization before decorative effects.

3.2 Design Supports Content

Visual design should make information easier to understand and use.

Content should not be forced into a component simply because that component exists. A page does not require cards, illustrations, icons, or callouts unless they improve comprehension, navigation, or interaction.

3.3 Accessibility Is a Foundation

Accessibility is part of the design process from the beginning. SalvageCars.com should aim to conform to WCAG 2.2 Level AA.

Design and implementation should consider sufficient color contrast, readable font sizes and line spacing, comfortable line lengths, keyboard navigation, visible keyboard focus, semantic heading structure, descriptive links and controls, adequate touch-target sizes, screen-reader compatibility, zoom and text resizing, reduced-motion preferences, and information that does not depend on color alone.

Accessibility requirements should influence component design before implementation rather than being added as a final correction.

3.4 Consistency Builds Trust

Similar information and actions should look and behave similarly throughout the site. Visitors should be able to learn the site's visual language naturally.

3.5 Authority Should Be Clear

SalvageCars.com combines plain-language guidance with authoritative external information. The interface should make that distinction clear.

Official information may include state motor vehicle agencies, statutes, regulations, government forms, and other primary sources.

The design must never imply that SalvageCars.com is a government agency or that its guidance replaces official requirements.

3.6 Design Supports User Journeys

Jobs To Be Done, user questions, navigation paths, and user journeys are defined in Site Structure & User Navigation.

The design system should make those paths easy to recognize and follow, but they must not depend on a particular visual component.

3.7 Progressive Enhancement

Core information and navigation should remain usable without unnecessary reliance on complex interfaces. Enhancements may improve the experience, but essential information should not depend on them when a simpler accessible approach is practical.

3.8 Mobile Is Not Secondary

Pages should work well on small screens as well as large displays. Content hierarchy must remain understandable when layouts collapse into a single column.

Part II

Visual Foundations

4.1 Overall Visual Direction

The visual character of SalvageCars.com should be:

Clean. Calm. Practical. Authoritative. Approachable.

The site should avoid appearing busy, aggressively commercial, overly promotional, automotive-themed for decoration alone, visually intimidating, or like an auction marketplace when presenting educational information.

4.2 Typography

SalvageCars.com should use Inter as its primary typeface, with a system sans-serif fallback stack.

font-family: Inter, ui-sans-serif, system-ui, -apple-system,
BlinkMacSystemFont, "Segoe UI", sans-serif;

Typography should optimize readability before visual distinctiveness. One primary typeface should be used throughout the site unless a future need clearly justifies another.

Body text should use an approximate line height of 1.65. Long-form content should generally target approximately 60–75 characters per line.

Headings should use relatively tight line heights: approximately 1.15 for H1, 1.2 for H2, and 1.3 for H3.

4.3 Page Widths

  • Site container: maximum width approximately 1200px.
  • Reading container: maximum width approximately 720–760px.

Standard horizontal page padding should be approximately 24px on mobile and 32px on larger screens.

4.4 Spacing Scale

Use Tailwind's standard spacing scale rather than custom values without a clear need.

  • Very small separation: 4–8px
  • Related elements: 12–16px
  • Paragraph / component spacing: 16–24px
  • Subsection spacing: 32px
  • Major section spacing: 48–64px
  • Large page section: 80px

Elements that belong together stay close; different ideas get more space.

Informational states may use blue, green, amber, and red as appropriate, but these colors should be used sparingly and never as the sole means of communicating meaning.

4.6 Borders, Corners, Shadows, and Surfaces

  • Use 1px borders with #e2e8f0 when separation is needed.
  • Use a default border radius of approximately 6px.
  • Avoid pill-shaped elements unless a specific component requires them.
  • Use no shadow by default.
  • Use subtle shadows only when elevation communicates a real interface relationship.
  • Use #f8fafc as the primary page background and #ffffff as the primary content surface.

Default to open space before adding a container. Default to a container before adding decoration.

Part III

Universal Interaction & Component Rules

5.1 Links

Inline links should use #1d4ed8 and be underlined by default so they do not depend on color alone for recognition.

Navigation links may omit underlines when their interactive role is visually obvious. Link text should be descriptive.

5.2 Focus States

Every interactive element must provide a clearly visible keyboard focus indicator. The default treatment should use an approximately 3px blue outline with a small offset.

5.3 Responsive Behavior

Use Tailwind's standard responsive breakpoints unless a real layout need requires a custom breakpoint. Design should be mobile-first.

5.4 Motion

Motion should be subtle and functional. Decorative animation should generally be avoided, and interfaces should respect prefers-reduced-motion.

5.5 Icons

Icons are supplemental and should not be required for comprehension. An icon should not be the sole label for an important action unless it has an accessible name and its meaning is reliably understood.

5.6 Component Independence

Information architecture and user journeys must not depend on a particular visual component. A JTBD path may begin as a simple text link and later become a card without changing the underlying journey.

Part IV

Implementation Guidance

6.1 Tailwind as the Primary Styling System

SalvageCars.com should use Tailwind CSS as the primary styling system for the current static site.

6.2 Prefer Tailwind Defaults

Prefer Tailwind defaults when they meet the design requirement. Create custom values only when the product has a real need for them.

This keeps implementation simple and avoids creating a second custom design language on top of Tailwind.

6.3 Initial Tailwind Mappings

  • max-w-7xl for the primary site container.
  • max-w-3xl for long-form reading width.
  • bg-slate-50 for the page background.
  • bg-white for primary content surfaces.
  • text-slate-900 for primary text.
  • text-slate-600 for secondary text.
  • border-slate-200 for standard borders.
  • text-blue-700 for primary links and actions.
  • hover:text-blue-800 for link hover states.
  • rounded-md as the default subtle corner treatment.

6.4 Information Hierarchy

The visual system should establish a clear progression from primary information to supporting information.

Editorial rules for writing headings, paragraphs, terminology, links, warnings, and other content belong in Content Standards.

6.5 Future Components

Buttons, cards, callouts, tables, forms, navigation components, and other reusable patterns should be added to this document when their real use cases are understood.

Cards are not required for initial JTBD navigation or for launch.

7. Design System Evolution

This document is a living standard and should remain the authoritative source for SalvageCars.com visual and interaction decisions.

As new needs emerge, this document may be expanded with additional component specifications and implementation guidance.

Need → Pattern → Standardize → Reuse

Clarity over decoration. Consistency builds trust. Design helps visitors understand their situation and know what to do next.
